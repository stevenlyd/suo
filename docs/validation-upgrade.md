# Strict validation in 0.6.0

TypeScript checks declarations, imports and typed object shapes. Runtime validation checks untrusted JSON, canonical object references, graph topology, cross-record relationships, frozen digests and lifecycle invariants. Both are required. Neither proves behavioral correctness, authenticates a person's identity nor verifies a remote provider from a supplied URL.

The shared runtime schema validates every proposal/closure envelope and operation payload. Unknown properties are rejected. The CLI and core mutation APIs apply these guards before returning staged or committed state; persistence also validates the merged on-disk pending proposals before writing. A fresh proposal must contain the `expectedRevision` actually observed with `inspect`; omission is an error. Never fill it with a newly fetched number without reviewing intervening changes. Revisions are local to the selected authority lineage, not globally unique cross-branch identities. Independent bounded edits retain the existing digest conflict rules.

Contracts declare `requiredChecks: [{ id, description }]` and `checkRationale`. Drafts may explicitly contain an empty rationale, but cannot freeze until it is meaningful. An empty check set is valid only with an explicit rationale explaining why no deterministic checks are required. This is a Product decision, not an inferred default. No universal test suite is imposed.

Frozen handoffs must contain their complete frozen definition. Acceptance IDs and check IDs are unique. Closures supply the observed `handoffRevision`, implementation references with exact `revision`, exact coverage of frozen acceptance IDs and required check IDs, and meaningful evidence for each passing result. Each check declares `id`, `revision`, `result` and (when passing) `evidenceRef`; its revision must match a supplied implementation reference. Unknown IDs, duplicates and omissions fail submission. Failed/not-run results can be recorded for review but cannot be accepted. Acceptance evaluates the frozen contract, not a later draft. Unresolved Product questions/deviations block acceptance, including when loading persisted accepted records.

Evidence remains **provided**, not independently verified. Before submitting or accepting, the agent must gather fresh authoritative source evidence (actual check run, exact commit, observed behavior), inspect identifiers/revisions/results, and disclose unavailable verification. This provider-neutral kernel has no remote evidence adapter; it does not turn input into a provider-verified receipt. Agent/verifier strings are declared identities, not authenticated principals. Product acceptance is separate from live-user acceptance and deployment permission.

## Explicit completion of older records

0.6.0 deliberately rejects incomplete older records. There is no legacy acceptance path, automatic pass, guessed check rationale or borrowed current frozen definition. Keep the old runtime for read-only audit/recovery; its acceptance of a record does not establish validity under 0.6.0.

1. Preserve a byte-for-byte backup of source, imported files, Vault notes/marker/history and staged proposals, plus their Git SHA and runtime version. Work in a separate reviewed copy. Never rewrite the only audit archive or alter a running project's history to silence validation.
2. Export a raw compiled snapshot with the matching historical runtime, or use the snapshot member of a saved history record. Run `suo diagnose /absolute/path/raw-snapshot.json` with 0.6.0. It reads only that JSON, returns `needs-completion` and field/invariant diagnostics with nonzero status, and never loads or changes project authority. Malformed JSON is an error. A valid result means structural validity only.
3. Inventory every diagnostic. Recover original frozen definitions and observed proposal baselines only from exact original source/history evidence. Supply required-check declarations/rationale through explicit Product review. Obtain missing acceptance/check evidence by running or observing the actual checks at the relevant implementation revision. Do not relabel later evidence as historical evidence. Missing decisions or genuine evidence remain blocked/needs-completion.
4. Prepare the complete typed authority in the isolated copy and validate it with the new runtime. Preserve original records separately with conversion provenance and review the full diff. Vault history is hash chained and append-only: this release provides **no automatic history converter**. Do not hand-rehash history to imply original approval. If archived history lacks required facts, stop that Vault upgrade and report the missing facts and a separately approved migration design.
5. Only adopt the completed authority after review and authorization; run `check`, the relevant tests and native runtime/skill version checks. Retain rollback and the untouched original archive. A pending proposal lacking its real observed baseline should be resubmitted after fresh semantic review, not silently stamped with the current revision.

For metadata already valid under the strict model, the existing reviewed `correct_handoff_product_revision` operation remains available with fixed evidence and its correction audit. Invalid input cannot use that operation to bypass validation; diagnose and complete the isolated copy first. This release does not migrate PIC or any other live project and introduces no shared/global authority semantics.
