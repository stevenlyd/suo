# Schema 5 cutover

Schema 5 is one current-state Unit model. Old module/handoff/realization/closure or Vault current-state data is not valid new authority. Do not add legacy bypasses or silently default unknown checks/evidence to success. Preserve old files in Git or an explicit backup while preparing a reviewed candidate; do not retain a parallel current ledger.

1. Pin each branch independently and export its old current definitions with the matching reviewed old runtime (`loadAuthority` for TS). Keep the old runtime for inspection/recovery. Do not execute newly fetched unreviewed source. Fetch/reconcile concurrent edits before publication.
2. Map current modules to Units preserving stable IDs and normative definitions, included scope, exclusions, acceptance criteria and dependencies. Decompose only real independently meaningful deliverables; decisions usually remain decisions with alternatives, selected choice, rationale and prerequisites. Preserve unresolved and experimental choices. Do not copy main authority wholesale onto integration.
3. Map current handoff intent into the Unit definition and expected assignee. Map only genuinely known own integration obligations/check requirements; missing policies stay null. Old handoff generations and revision counters are not new validity requirements.
4. Realization/closure and historical CI/deploy/PR outcomes do not establish current implementation. Review current code and tests; map criteria to current source paths/symbols and bind content via `record`. Otherwise retain unknown/stale or partial coverage. Never turn zero realizations into acceptance. Do not migrate external current-state claims into Unit fields. Keep prior historical data in Git, not a new ledger.
5. For old Vault authority, prepare a Git-contained typed Unit registry from explicitly selected current notes. Preserve unrelated Vault notes. External `suo-state/current.json` is not copied into new authority; Markdown is a view after cutover. No dual writes.
6. Validate the candidate with schema-5 source/type/runtime checks and branch-specific semantic-preservation fixtures. Stage changes in an isolated worktree; inspect its complete diff, then commit/PR under normal CI/review. Existing Suo writes require an observed repository token; externally ignored authority cannot be overwritten as an unobserved candidate. Auxiliary files must be migrated explicitly, not silently deleted by the writer.
7. Coordinate Duet Unit-aware client and Suo schema/runtime versions. Publish only after matching clients/tests are ready. Install through native distribution plus the pinned Node runtime, preserving prior runtime/configuration. Installing a client does not migrate projects.

Rollback before new writes can select the prior client and prior Git state. After schema-5 writes, prefer fix-forward; any reverse migration needs a reviewed loss report and Git recovery point. Selecting an old runtime alone is not rollback. No live project deployment is required to migrate definitions.

Project tests/check policy are normative content; their execution outcomes are not. User acceptance or a particular new required-check policy must not be invented during migration. A meaningful missing product choice blocks only its dependent claim/work.
